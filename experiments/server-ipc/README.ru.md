# Взаимодействие компонентов Build 4311

17 ноября 2026 года сравнили TCP loopback, Unix stream и POSIX shared memory без игрового клиента. Затем запустили штатные игровые процессы с TCP и Unix-сокетами, измерили чтение роли через `gamedbd` и регистрацию `is61`.

## Результат

- `type=unix` работает в штатных бинарниках 4311. Проверены `logservice`, `uniquenamed`, `gamedbd`, `gdeliveryd`, `glinkd` и `gs is61`, включая регистрацию карты и успешное чтение роли.
- В WSL2 Unix-сокеты уменьшили медиану задержки обмена сообщениями на 19–25% относительно TCP loopback. Для `GetRoleBase` на закреплённых CPU медиана составила 119,889 мкс по TCP и 106,402 мкс через Unix, снижение около 11%.
- Для обмена по 64 Б суммарные затраты CPU двух процессов сократились с 13,552 до 10,214 мкс на обмен, примерно на 25%.
- У SHM с блокирующими семафорами оказались самые низкие затраты CPU. Задержка ответа в этом тесте была 21,9–34,3 мкс.
- Для `type=shm` штатные `logservice` и `uniquenamed` сохранили процессы, но канал и shared mapping между ними отсутствовали. Для такого транспорта потребуется реализация на обеих сторонах GNET.
- Регистрация нового процесса `is61` заняла около 7,2 секунды в обоих режимах. Входные файлы были в прогретом файловом кэше WSL.
- MariaDB работала за отдельным `veth` и обслуживала `licenseservice` по TCP. Игровые службы использовали собственное сетевое пространство.

Для дальнейшей конфигурации выбран штатный `type=unix` для проверенных внутренних GNET stream-связей. MariaDB размещается в отдельном контейнере с подключением по TCP. Измерения SHM сохранены в протоколе как результат исследования транспорта.

Клиентский прогон на рабочей VM подтвердил вход, движение, интерфейсы, телепорт внутри полного `gs01` и повторный вход в сохранённую позицию. `gauthd`, `gfactiond` и `gacd` установили Unix-соединения. После перезапуска `logservice` семь служб восстановили свои Unix stream за 2,391 с, игровой сокет сохранился. [Протокол клиентского прогона](client-check.ru.md)

## Условия измерений

Хост с Intel Core Ultra 7 268V. Pengwin WSL2, Linux `6.18.33.2-microsoft-standard-WSL2`, glibc `2.41`, GCC `14.2.0`, восемь доступных CPU. Docker в этом этапе отсутствовал. Все метрики относятся к этому окружению и указанной нагрузке.

В микроизмерении C-процессы закреплены за CPU 2 и 3. Соединения создаются до таймера, затем идут 2000 разогревающих обменов. Одна операция включает запрос и эхо-ответ одинакового размера. Для каждого размера и транспорта выполнено семь серий с перемешиванием порядка. В таблицах приведены медианы статистик отдельных серий.

TCP использует `127.0.0.1` и `TCP_NODELAY` на обеих сторонах. Unix использует именованный `AF_UNIX/SOCK_STREAM`. SHM использует `shm_open`, `mmap(MAP_SHARED)`, два process-shared `sem_t` и копирование запроса и ответа. Оба процесса ожидают события блокирующим `sem_wait`. Проверяются последовательность и содержимое эхо-ответа.

`cpu_us` — сумма процессорного времени двух процессов на один обмен. `echo_mib_s` в CSV — объём запроса и ответа за время последовательных обменов. Таймер запускается после подготовки соединения и создания SHM. [Методика AF_UNIX](https://man7.org/linux/man-pages/man7/unix.7.html) · [POSIX SHM](https://man7.org/linux/man-pages/man3/shm_open.3.html) · [Семафоры между процессами](https://man7.org/linux/man-pages/man3/sem_init.3.html)

## Штатные процессы и GNET

Тестовые копии запускаются в Linux namespaces для сети, монтирования и IPC. Рабочие каталоги, WDB и журналы находятся в отдельных временных каталогах Linux. `/home` закрыт собственным `tmpfs`, в него помещается оригинальный `license.conf` раздачи. MariaDB запущена в дополнительном сетевом пространстве и имеет адрес `198.18.108.2`. Игровая сторона `veth` имеет адрес `198.18.108.1`, маршрут по умолчанию отсутствует у обеих сторон. В JSON сохранена SQL-сессия `licenseservice` с адреса игровой стороны.

В начале пробы `gamedbd` завершался через `kill(0, SIGUSR1)`. `strace` последовательно показал отсутствие `/home/license.conf`, затем отказ подключения к `127.0.0.1:33000` после предоставления файла. Со штатным `licenseservice` и его SQL-схемой тот же бинарник успешно открыл WDB. Поэтому каждый дочерний игровой процесс в тестовом коде получает отдельную группу через `start_new_session=True`.

| Связь | Результат Unix-прогона |
| --- | --- |
| `uniquenamed → logservice` | Установлен Unix stream, сервер создал журнал. |
| `gamedbd → logservice` | Установлен Unix stream. |
| `gdeliveryd → gamedbd` | Установлен Unix stream. Отдельный тестовый клиент успешно выполнил RPC к тому же `gamedbd`. |
| `gdeliveryd → uniquenamed` | Установлен Unix stream. |
| `glinkd → gdeliveryd` | Установлен Unix stream. |
| `is61 → gdeliveryd`, `glinkd`, `gamedbd`, `logservice` | Четыре установленных Unix stream. Координатор зарегистрировал `index=101`, `worldtag=161`. |

Игра сохраняет отдельный TCP-слушатель прямых связей `gs`, а `glinkd` — клиентский TCP-вход. Прямые локальные связи между GS уже использовали `/tmp/gssock_*` в исходном стенде. Следующий этап включает остальные службы, полную клиентскую сессию и перезапуски. [Исходный снимок связей](../../research/runtime-contracts.ru.md) · [Пробы режимов](evidence/gnet-transport-probe.json) · [Сокеты и регистрация карты](evidence/native-map-starts.json)

В GNET H176 обе стороны `ActiveIO` и `PassiveIO` выбирают между `tcp`, `udp` и `unix`. Для внутренних GNET stream-связей в испытанных бинарниках достаточно изменить `type` и `address` на обеих сторонах. Значение `address` для Unix — полный путь одного и того же сокета. Поле `port` осталось в копиях конфигов. Unix-ветка выбирает адрес по `address`. [ActiveIO](https://github.com/huzeming/176source/blob/c0992a29/share/io/activeio.h) · [PassiveIO](https://github.com/huzeming/176source/blob/c0992a29/share/io/passiveio.h)

Пример пары настроек для измерения.

```ini
[GameDBServer]
type = unix
address = /run/pw/gamedbd.sock
port = 29400

[GameDBClient]
type = unix
address = /run/pw/gamedbd.sock
port = 29400
```

У GS эта клиентская секция называется `[GamedbClient]`. В контейнере общий каталог `/run/pw` нужно создавать до запуска служб. При переносе других пар сверять ограничения адресов и протокольную готовность конкретного компонента.

## Чтение роли через gamedbd

Выполнен `GetRoleBase`, RPC `3013`, для роли `16` из архивной WDB. В каждой серии 300 разогревающих чтений и 5000 измеряемых. Все результаты имеют `retcode=0`, длину значения 835 Б и одинаковый SHA-256. Проверяются тип протокола, XID, код возврата, длина и контрольная сумма значения. Содержимое роли в доказательства не записывается. [Описание RPC](https://github.com/huzeming/176source/blob/c0992a29/cnet/rpcalls.xml) · [Код клиента измерения](rpc_bench.py)

| Условия | Транспорт | Серии | p50, мкс | p95, мкс | p99, мкс |
| --- | --- | --- | --- | --- | --- |
| Планировщик WSL выбирает CPU | TCP | 4 | 203,05 | 362,53 | 489,03 |
| Планировщик WSL выбирает CPU | Unix | 4 | 192,77 | 357,07 | 496,85 |
| Клиент CPU 2, gamedbd и его потоки CPU 3 | TCP | 7 | 119,89 | 226,10 | 301,77 |
| Клиент CPU 2, gamedbd и его потоки CPU 3 | Unix | 7 | 106,40 | 207,13 | 272,92 |

Закреплённые серии дают уменьшение p50 примерно на 11%, p95 — на 8,4%, p99 — на 9,6%. Первые серии показывают заметный разброс от планирования. Выбор CPU и число потоков требуют проверки под полной игровой нагрузкой. Сохранение роли, обработка многих сессий и аварийное восстановление требуют отдельных замеров. ## Загрузка карты

После подъёма служб запускается новый `./gs is61 gs.conf gmserver.conf gsalias.conf`. Время считается от `Popen` до строки регистрации карты у `gdeliveryd` в `world2.trace`, с опросом раз в 100 мс. Соседняя игровая карта в этих прогонах отсутствует.

| GNET-транспорт | Повторы | Минимум, с | Медиана, с | Максимум, с |
| --- | --- | --- | --- | --- |
| TCP loopback | 3 | 7,126 | 7,226 | 7,227 |
| Unix stream | 3 | 7,127 | 7,229 | 7,230 |

Для обоих режимов процесс прочитал около 328 МБ через `read`. Входные страницы к этому времени были закэшированы. Холодный диск и готовность прямого маршрута от работающего исходного GS требуют собственного замера. Порядок серий — Unix, TCP, TCP, Unix, Unix, TCP. Ускорение регистрации от смены транспорта в этом опыте отсутствовало. [Все прогоны](evidence/native-map-starts.json)

## Контейнеры и следующие измерения

1. В игровом контейнере испытать Unix-сокеты для подтверждённых GNET-связей. На рабочей VM проверены клиентский вход и перезапуск `logservice`. Игровые операции гильдии и восстановление остальных служб требуют отдельных сценариев. [Клиентский прогон](client-check.ru.md). Для SQL оставить TCP до отдельной MariaDB. Поля host и port MariaDB Connector/C поддерживают удалённое соединение, Compose предоставляет сеть и DNS имён сервисов. Поведение каждого бинарника с DNS-именем проверить отдельно. [MariaDB Connector/C](https://mariadb.com/docs/connectors/mariadb-connector-c/api-functions/mysql_real_connect) · [Сети Compose](https://docs.docker.com/compose/how-tos/networking/)
2. Для времени холодного перехода измерять загрузку ресурсов, регистрацию у координатора и появление `Add dispatcher` раздельно. В прошлом опыте карта регистрировалась примерно за 4,2 с, затем требовалось ещё около 18 с для прямого маршрута. Период повторного подключения между GS в исследованном H176 составляет 15–24 с. Следующий кандидат для ускорения — повторное подключение к только что поднятой карте. [Маршрутизация](../../research/maps.ru.md#готовность-и-выбор-маршрута)
3. Измерить холодный и прогретый файловый кэш, размещение ресурсов на файловой системе Linux и объём стартового stdout. В шести прогонах `is61` stdout составлял около 2 МБ. Для контейнера проверить постоянные тома WDB и журналов. Docker указывает на дополнительную работу writable layer при изменении файлов. [Тома Docker](https://docs.docker.com/engine/storage/volumes/)
4. Проверить thread pools, affinity и количество GS при ожидаемом числе персонажей. После выявления горячей связи сравнить пакетную отправку и SHM с блокирующим уведомлением. В контейнере объём `/dev/shm` задаётся отдельно через `shm_size`. [IPC и shared memory Docker](https://docs.docker.com/reference/cli/docker/container/run/#ipc-settings---ipc)

## Повторение

Микроизмерение требует Linux, C-компилятора и Python 3. Запуск из каталога опыта.

```bash
python3 run-ipc.py --repeats 7 --cpus 2 3 --output ipc.csv
```

Для штатного контура нужны копии файлов раздачи и Linux-утилиты `ip`, `unshare`, `nsenter`, `taskset`. [probe-gnet.py](probe-gnet.py) проверяет простой контур `logservice` и WDB-служб и предоставляет общие функции конфигурации и наблюдения. [probe-stack.py](probe-stack.py) поднимает MariaDB в дополнительном пространстве и штатный `licenseservice`, затем выполняет выбранные серии. Оба скрипта требуют предварительно изолированной сети. Оригинальные данные используются как входы для временных копий.

В `fixtures/assets` нужны `logservice` с `logservice.conf`, `licenseservice` с `gamesys.conf`, `glinkd` с `gamesys.conf`. В `fixtures/wdb` нужны каталоги `uniquenamed`, `gamedbd`, `gdeliveryd` из раздачи с конфигами, их ресурсами и архивными WDB. В `fixtures/gs` нужны `gs`, `gs.conf`, `gmserver.conf`, `gsalias.conf` и `script.lua`. `fixtures/runtime` содержит `license.conf`, `root/sql/licenseservice.sql`, общие файлы `root/pwserver/gamed/config`, каталог карты `a61` и штатные конфиги `gamed`. Скрипт использует штатный параметр `1` при запуске `glinkd`.

В текущем прогоне MariaDB 11.8.6, `libmariadb3`, PCRE1 8.39 и strace с зависимостями распакованы во временный каталог `/tmp/pw-ipc-tools.*` через `apt-get download` и `dpkg-deb -x`. Корень такого каталога передаётся как `tools`. Структура `tools/usr` содержит программы и данные MariaDB. Для PCRE1 использован пакет Debian Bookworm `libpcre3_8.39-15_amd64.deb` с SHA-256 `993ea623ce5b42d67f653f2faaa7ef15e7c9d72bfcb93e22a1eaff7aa3532303`.

Пример запуска после подготовки `fixtures` и `tools`.

```bash
bench_dir="$PWD"
fixtures=/absolute/path/to/fixtures
tools=/absolute/path/to/unpacked-packages
output="$PWD/native-map-starts.json"

unshare --user --map-root-user --mount --net --ipc sh -eu -c '
  umask 077
  mount -t tmpfs -o mode=0755,nodev,nosuid tmpfs /home
  install -m 600 "$2/runtime/license.conf" /home/license.conf
  ip link set lo up
  export LD_LIBRARY_PATH="$3/usr/lib/x86_64-linux-gnu:$3/lib/x86_64-linux-gnu"
  exec python3 -B "$1/probe-stack.py" \
    --assets "$2/assets" --wdb "$2/wdb" --gs "$2/gs" \
    --fixture "$2/runtime" --tools "$3" --output "$4" \
    --map-seconds 30 --modes unix tcp tcp unix unix tcp
' sh "$bench_dir" "$fixtures" "$tools" "$output"
```

Для чтений роли в той же команде заменить аргументы измерения на `--rpc-count 5000 --rpc-role 16 --rpc-cpus 2 3 --modes tcp unix unix tcp unix tcp tcp unix unix tcp tcp unix tcp unix` и выбрать отдельный файл результата. В конце каждого прогона тестовые процессы завершаются, временные WDB и SQL-каталоги удаляются. Файлы конфигурации рабочего сервера сохраняют исходные значения.
