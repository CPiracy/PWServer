# Клиентский прогон Unix-сокетов Build 4311

17 ноября 2026 года на рабочей Debian VM проверили штатные бинарники 4311 с внутренними GNET-соединениями через Unix stream. Клиент подключался к обычному адресу `192.168.56.101:29000`. Действия в игровом интерфейсе выполнял пользователь.

## Подготовка

Перед переключением активных клиентских сессий на `29000` было 0. Остановили два участка мира из опыта с Сетью и прежний `is61`, затем сетевые службы. `gamedbd` и `uniquenamed` завершили работу по `quit_lockfile` после контрольной точки. После завершения скопировали обе WDB в `/root/pw-ipc-client-lab/backups/`.

В `/root/pw-ipc-client-lab/configs/` создали копии конфигураций с 44 изменёнными GNET-секциями. На обеих сторонах stream-соединений задали `type=unix` и согласованный путь в `/run/pw-ipc-test/`. Манифест сохраняет название секции, прежний порт и выбранный сокет. Рабочие каталоги служб и файлы WDB используются штатные.

Запущены `logservice`, `uniquenamed`, `gamedbd`, `gauthd`, `gacd`, `gfactiond`, `gdeliveryd`, `glinkd`, полный `gs01` и `is61`. Основной мир использует исходные полные `base_region` и `local_region`, а также `height_limit=800.0`. SQL обслуживала MariaDB рабочей VM по TCP. Раздельное сетевое пространство MariaDB проверено в [предыдущем этапе](README.ru.md).

## Проверки

| Действие | Подтверждение |
| --- | --- |
| Вход за `tptest` | `userid=1024`, `roleid=1027`, авторизация вернула `retcode=0`, `PlayerLogin_Re` вернул `result=0`, выбран `gs_id=1`. |
| Ходьба клавишами и мышью, рюкзак и карта | Пользователь подтвердил обычную работу. Все десять процессов продолжали работу. |
| Телепорт из Тайной деревни в Город Мечей | Пользователь подтвердил прибытие и движение. Обе точки обслуживает полный `gs01` с `worldtag=1`. |
| Выход до экрана логина | Журнал зарегистрировал `RoleOffline(1027)`, клиентская TCP-сессия завершилась. |
| Проверка сохранённой позиции | `GetRoleStatus` по Unix-сокету вернул `retcode=0` и новые координаты в Городе Мечей. |
| Повторный вход | Пользователь подтвердил появление в точке последнего выхода. |
| Перезапуск `logservice` при активном клиенте | Семь клиентов восстановили Unix stream за 2,391 с, игровой сокет сохранил inode `617579`. Все десять процессов работали. |
| Управление и выход после переподключения | Пользователь подтвердил обычное управление и успешный выход. Журнал зарегистрировал второй RoleOffline, активных клиентских сессий стало 0. |

Read-only RPC `GetRoleStatus` имеет тип `3015`. До обратного телепорта сохранённая позиция роли составляла `(972.134094, 225.024292, 3193.952637)`, после выхода — `(513.492493, 216.570374, 3186.244141)`. В обоих ответах `worldtag=1`, уровень 20. После второго выхода сохранена позиция `(509.066162, 219.020493, 3165.272217)`. На этапе проверки прочитаны только версия, уровень, позиция, тег и открытые точки телепорта.

При перезапуске PID `logservice` изменился с `26388` на `26994`. Восстановились `gamedbd`, `gdeliveryd`, `gfactiond`, `glinkd`, `gs01`, `is61` и `uniquenamed`. Клиентский TCP-сокет проверялся в течение ожидания восстановления, с шагом примерно 250 мс.

В журнале входа также зафиксирована строка `OnPlayerLogin, arena player 1027 not found! SEND DB PACKET`. Её причина требует отдельного исследования. Результат входа роли в этом прогоне — `0`, пользователь подтвердил управление, телепорт и повторный вход.

## Граница проверки

Подтверждены клиентский вход, интерфейсы, движение, внутримировой телепорт и повторный вход с сохранённой позицией. Перезапуск проверен для `logservice`. Передача персонажа между разными GS, игровые операции гильдии и восстановление остальных служб требуют собственных сценариев.

Рабочая VM сейчас использует тестовые Unix-конфиги и полный основной мир. Команды прежних процессов сохранены в `/root/pw-ipc-client-lab/baseline.json`, актуальные команды — в `launched.json`. Копии конфигураций с реквизитами SQL и WDB хранятся в приватном каталоге VM.

## Код и повторение

[Подготовка, запуск и состояние VM](vm-client-probe.py) создают отдельные конфиги, сохраняют команды запуска, завершают WDB по контрольной точке и запускают штатные ELF. Доступны команды `prepare`, `run`, `status`. Подготовка рассчитана на свежий каталог `/root/pw-ipc-client-lab`. Каждый игровой процесс получает отдельную группу процессов.

[Проба переподключения журналов](restart-logservice-probe.py) требует активного клиента и подготовленных `launched.json`. Она перезапускает `logservice` с теми же аргументами, ждёт восстановления исходного набора клиентов и проверяет неизменность игрового сокета. Для повторения на VM путь к файлу контроллера в коде согласовать с его размещением.

## Ожидание холодной карты

В исследованном H176 повтор после неудачного прямого подключения GS задаётся выражением `rand() % 10 + 15`, то есть 15–24 с. Это согласуется с дополнительным ожиданием около 18 с в опыте с холодной целью. Изменение длительности таймера потребует изменения кода. При выбранном использовании штатных настроек готовность достигается запуском карты заранее и ожиданием прямого маршрута до игрового действия. Полный `gs01` обслуживает весь основной мир одним процессом.
