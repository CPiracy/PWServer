# Панели и эксплуатационные сценарии PW 1.7.6 Build 4311

В предыдущей проверке в VM работали **PWAdmin `/pwadmin176new/`**, **Adminer 5.3.0** и **PHP IWEB с `iwebx32`**. Для нового опыта выбран **Java IWEB 1.7.6 Talolan**. В его архиве есть JAR, JDK 8u301 и JDBC-конфигурация для `pw176`. **PWAdmin Suite .NET** описан по исходникам и архиву. Авторские проверки этой панели относятся к 1.7.3.

Наблюдения о работающей 4311 взяты из отчёта предыдущей проверки VM. Для этого этапа сверены JSP, исходники и выборочные файлы архивов, а Java IWEB запущен отдельно в WSL. [Архитектура 4311](rutracker-1.7.6-4311-architecture.ru.md) · [Входы в панели VM](rutracker-1.7.6-4311-usage.ru.md) · [Проба Talolan](../experiments/server-validation/server-only-validation.ru.md#java-iweb-talolan)

## Где исполняется операция

- **MariaDB.** `pw176.users` содержит игровые учётки, `pw176.auth` — права с привязкой к пользователю и зоне. `gauthd` использует `acquireuserpasswd` для проверки входа. JSP вызывает `adduser`, `addGM` и `usecash` через JDBC. Доступ веб-оператора проверяется своим механизмом в каждой панели. [Архитектура 4311](rutracker-1.7.6-4311-architecture.ru.md), `pwadmin/webapps/pwadmin176new/account.jsp:89`.
- **Игровые RPC.** На 4311 по отчёту наблюдались подключения к `gdeliveryd` на `29100` и `29300` и к `gamedbd` на `29400`. Первые два порта обслуживают разные связи, `glinkd → gdeliveryd` и `gs → gdeliveryd`. Проверка доступности порта устанавливает только состояние TCP. Подтверждение операции даёт игровой ответ и независимая проверка эффекта. JSP `status.jsp` запрашивает `DeliveryDB.GetMaxOnlineNum`. В Java IWEB и .NET есть реализации управления через `GameDB` и `DeliveryDB` или их аналоги. [Связи служб 4311](rutracker-1.7.6-4311-architecture.ru.md), `pwadmin/webapps/pwadmin176new/status.jsp:35`.
- **Файловые БД и нативный CLI.** Состояние персонажей и уникальных имён распределено по `gamedbd` и `uniquenamed`. Оба держат открытыми собственные `dbhome/dbdata` и `dbhome/dblogs`. В JSP для списка и экспорта запускается отдельный экземпляр `gamedbd` с `gamesys.conf` и разбирается результат. Редактор XML пишет временный файл и запускает комплектный `updater`. Разница между RPC и CLI существенна для прав, путей к данным и конкурентного доступа. [Файловые БД 4311](rutracker-1.7.6-4311-architecture.ru.md), `pwadmin/webapps/pwadmin176new/role.jsp:23`, `pwadmin/webapps/pwadmin176new/rolexml.jsp:198`.
- **ОС и локальные файлы.** `ps`, конфиги служб, журналы и сигналы читаются или применяются в контексте Linux-хоста. Порядок старта, рабочие каталоги, аргументы карт и готовность служб задаёт конфигурация PW. Отдельно стоящей веб-панели с одним сетевым подключением к MariaDB нужны собственные каналы для этих действий и для ролевой БД. [Штатные скрипты 4311](rutracker-1.7.6-4311-architecture.ru.md), `pwadmin/webapps/pwadmin176new/serverctrl.jsp:27`.

## Матрица сценариев

**Проверено** означает наблюдение на 4311 в предыдущем отчёте. **Код** означает найденную реализацию, для которой система ещё должна показать результат. Классы Java IWEB в таблице относятся к содержимому JAR. Методы .NET относятся к архиву исходников. По проверенному PHP IWEB подтверждён просмотр процессов, детализация его остальных операций требует отдельного просмотра исходников этой PHP-поставки.

Cockpit может управлять юнитами, наблюдать журналы и ресурсы, а Webmin — обслуживать процессы, файлы и службы. Управление аккаунтами игроков остаётся задачей SQL с контрактом `gauthd`. Персонажи, игровые эффекты и операции над миром зависят от RPC, родных утилит и форматов PW. Для интерфейса обслуживания достаточно сначала определить, какой роли оператора требуется каждый канал. [Cockpit и журнал](https://docs.cockpit-project.org/cockpit-guide/latest/guide/features.html), [модули Webmin](https://webmin.com/docs/modules/bootup-and-shutdown/), [документация systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html).

## Порядок проверки с запущенным сервером и без игрового клиента

1. **Снять исходное состояние на изолированной копии 4311.** Зафиксировать версию сборки, конфиги, рабочие каталоги, PID, слушающие сокеты, аргументы `gs01`/`is61` и последние сообщения о загрузке. Получить схему `pw176` и список процедур без выборки реквизитов. Подготовить снимок, отдельную тестовую веб-учётку, тестовую игровую учётку и существующего офлайн-персонажа для чтения.
2. **Проверить опорные интерфейсы.** Войти в PWAdmin и PHP IWEB, сравнить статус обеих панелей с выводом `ps`/`ss` и журналами. В Adminer открыть ожидаемые таблицы и процедуры. У PHP IWEB проверить доступность `iwebx32` и соответствие конфигурации фактическим адресам. Для phpMyAdmin отдельный результат — успешная сессия и просмотр структуры при согласованной схеме HTTP/HTTPS, если нужен второй SQL-интерфейс.
3. **Поднять Java IWEB отдельно на копии 4311.** Сверить схему и параметры подключения из `application.yml`, подготовить тестовый вход `adminuser` и проверить свободный TCP `9898`. Начать с веб-входа, просмотра процессов и чтения онлайна. Сверить список персонажей и прочитанные поля с эталонным `exportrole`, полученным комплектным бинарником на холодной копии. Зафиксировать версию JAR, код возврата и несовпадения полей. Если придётся сравнить .NET, начать с проверки подключения и чтения после сверки SQL-схемы и формата роли. Нативный контроллер и BackupOps .NET проверяются отдельно после адаптации путей к 4311.
4. **Проверить обратимые записи.** Создать временную учётку через панель, проверить ID в MariaDB, выдать и отозвать GM для тестовой зоны, сверить результат в `auth`. Для одного офлайн-персонажа менять одно поле только после успешного сопоставления экспорта. Повторный экспорт должен подтвердить целевое изменение и сохранность соседних данных. Закрыть временную сессию и восстановить тестовые данные из снимка.
5. **Проверить обслуживание и восстановление.** Начать с одной тестовой карты, сверить PID, параметры запуска, журнал и связь `gs` с `gdeliveryd`. Полный стек останавливать штатным сценарием на отдельной копии с проверкой закрытия файлов БД и повторного запуска. Для резервной копии проверять и SQL, и `dbhome` обеих игровых БД. При логическом SQL-дампе проверить включение хранимых процедур, включая `acquireuserpasswd`, `adduser` и `addGM`. Завершить восстановлением в чистую копию и повторной сверкой учётки, GM-прав и экспорта персонажа. [MariaDB о дампах и процедурах](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump).

В журнале испытаний достаточно фиксировать операцию, сборки сервера и панели, ожидаемый результат, ответ панели, наблюдение из второго источника и результат отката. Вход в мир, отображение GM-функций, приём почты и broadcast, воздействие на активную сессию и фактические игровые рейты требуют отдельной проверки в клиенте.
