# Виртуальный клиент Perfect World для нагрузочных проверок

Цель — воспроизводить вход и игровые действия нескольких персонажей на изолированном сервере без графического клиента. Такой сценарий нужен для продолжения [замеров OverlayFS и симлинков](overlayfs-vs-symlinks-performance.ru.md) и других испытаний работающего сервера.

## Источники

Клиент найден в локальных клонах исходников. В 1.7.6 есть `cnet/gclient` с консольной точкой входа и `cnet/gclient/vclient` с игровым поведением. Один процесс создаёт сессии для заданного диапазона учётных записей. В локальном клоне 1.7.2 лежит готовый Linux ELF x86-64 и комплект Makefile. Первую проверку провели с этим бинарником. Сборка клиента из 1.7.6 описана ниже. [Точка входа 1.7.6](https://github.com/huzeming/176source/blob/c0992a29c0848de4de139a8958ceb11edcf2d38b/cnet/gclient/gclient.cpp) · [Makefile клиента 1.7.2](https://github.com/code-bynary/172source/blob/1c425175ae81a35b00d44e05e8e2c64513eabf05/cnet/gclient/Makefile)

## Воспроизведение входа

1. Поднять Build 4311 на копии данных в пространстве имён с отдельной сетью и временной MariaDB. Проба использовала девять штатных служб и карту `gs01`. Для World2 DB создали пустые записываемые `dbhome`. В MariaDB загрузили штатные SQL-дампы и добавили одну новую учётку процедурой `adduser`. [Подготовка чистого стенда](../experiments/package-layout/clean-start-experiment.ru.md)
2. Скопировать образец `gclient.conf` из клона 1.7.2 во временный рабочий каталог. В секции `Account` задать префикс, начало и конец диапазона и пароль тестовой учётки. Конец диапазона исключается. Для `prefix=pwbench`, `start=0`, `end=1` клиент создаёт одну сессию для `pwbench0`. `role=-1` разрешает выбрать первую подходящую роль. В `GLinkClient` указать loopback и порт шлюза внутри песочницы. Остальные настройки взять из образца этой версии. [Конфиг клиента](https://github.com/code-bynary/172source/blob/1c425175ae81a35b00d44e05e8e2c64513eabf05/cnet/gclient/gclient.conf)
3. После регистрации `gs01` запустить `gclient gclient.conf` из этого рабочего каталога. Проверить штатную авторизацию, список ролей, создание или выбор роли и вход в мир по сообщениям клиента и сервера. В клиенте факт входа отражается в счётчике `ENTERWORLD`.

## Ход проверки

Первый прогон подтвердил готовность девяти служб и `gs01`. Клиент 1.7.2 авторизовался на созданной учётке и получил список ролей. Сервер учёл одну сессию. Подтверждения входа в мир за 38 секунд не получили. Игровые действия и сравнительный замер нагрузки требуют успешного входа персонажей.

Код виртуального клиента предусматривает движение и хранит точки в локальном `move.data`. Этот файл относится к рабочему каталогу клиента. Воспроизводимый сценарий движения будет описан по успешному прогону. [Модуль движения](https://github.com/huzeming/176source/blob/c0992a29c0848de4de139a8958ceb11edcf2d38b/cnet/gclient/vclient/moveagent.cpp)

### Точная версия и параметры прогона

Использован готовый `cnet/gclient/gclient` из `code-bynary/172source` на ревизии `1c425175ae81a35b00d44e05e8e2c64513eabf05`. SHA-256 бинарника — `ae5ec264294064d2ad3c9fafbf63fd99db4f56128e03ae82e6d082a66b47d555`. Это Linux ELF x86-64. В локальном WSL он запустился с системными `libstdc++`, `libm`, `libgcc_s` и `libc`. Клиент в первых трёх прогонах брали из клона в готовом виде. Стартовые Makefile есть в 1.7.2. В проверенном дереве 1.7.6 их нет.

В повторном прогоне поднимали и `gs01`, и стартовую `is61`. Новые роли создаются на `is61` с тегом мира 161. Без этой карты координатор создавал роль и возвращал отказ при входе. Для чистого прогона сохранили базу и журналы в отдельных временных каталогах. Сервер и клиент видели только loopback, данные и SQL-дампы были доступны для чтения.

Для серии использовали `prefix=pwbench`, диапазон `start=0`, `end=4`, `role=-1` и `GLinkClient.address=127.0.0.1`, `port=29000`. Четыре синтетические учётки создали через `adduser` с одинаковым сгенерированным паролем. В используемом `gauthd` настроен формат `hash=3`. Для него в `adduser` передавали Base64 от MD5 имени учётки и пароля, а клиент получал исходный пароль. Перед запуском запросом к `auth` подтвердили отсутствие специальных прав у всех четырёх. В архивном SQL есть запись прав на первый автоматически назначаемый ID, поэтому его заняла служебная учётка, которую не использовали для входа.

Клиент запускали после регистрации двух карт. `stdbuf` даёт видеть текущие сообщения в журнале, когда stdout перенаправлен в файл.

```bash
stdbuf -oL -eL ./gclient ./gclient.conf
```

| Прогон | Наблюдение |
| --- | --- |
| Одна роль, только `gs01` | Штатная авторизация и создание роли прошли. Вход остановился на маршрутизации в мир 161, где GS ещё не был запущен. |
| Одна роль, `gs01` и `is61` | После переподключения GS подтвердил успешный `PlayerLogin_Re`. До полного входа по счётчику клиента проба не дошла. |
| Четыре обычные учётки, обе карты | Через 70 секунд все четыре сессии были авторизованы, клиент добавил четыре роли, GS подтвердил четыре входа. Счётчик клиента показал четыре подключения и ноль завершённых входов в мир. Изменений координат не зафиксировано. |

В исходниках завершение входа отмечается после получения `TASK_DATA`. До подтверждения этого этапа и движения четырёх игроков такую серию считаем проверкой совместимости клиента. [Обработка входа в игровой мир](https://github.com/huzeming/176source/blob/c0992a29c0848de4de139a8958ceb11edcf2d38b/cnet/gclient/vclient/player.cpp#L906-L933)

## Сборка из исходников 1.7.6

Собрали Linux ELF x86-64 в Debian WSL2 с GCC 14.2 и GNU Make. Исходники клиента, сгенерированные описания протокола и исходники Lua взяли из `huzeming/176source` на `c0992a29c0848de4de139a8958ceb11edcf2d38b`. В этом клоне отсутствуют правила сборки `gclient` и Lua, а также часть ссылок на общий код.

Для сборки понадобились правила Make из `code-bynary/172source` и две поправки для современных компиляторов, уже имеющиеся в этом клоне. В `marshal_x86_64.h` определения шаблонных операторов вынесены после определения `MarshalContainer`. В `luabase.cpp` убрана квалификация методов внутри класса. Остальные исходники игрового клиента и его сгенерированных протоколов оставлены из 1.7.6. Связали со включённой статической Lua и `libdl`. В итоговом ELF требуются только `libstdc++`, `libm`, `libgcc_s` и `libc`.

Ниже команды сборки в пустом временном каталоге. Пути в первых двух строках указывают на локальные клоны. На стенде `make` запускали через Bubblewrap без сети, с доступной только для чтения `/usr` и с временной копией исходников под `/work`.

```bash
source_176='/mnt/c/Users/admin/Documents/Perfect World Server/GitHub/huzeming-176source'
build_rules='/mnt/c/Users/admin/Documents/Perfect World Server/GitHub/172source'
client_build=$(mktemp -d)

git -C "$source_176" archive c0992a29c0848de4de139a8958ceb11edcf2d38b cnet share \
    | tar -xf - -C "$client_build"

for file in cnet/gclient/Makefile cnet/gclient/vclient/Makefile \
    share/mk/gcc.defs.mk share/mk/gcc.rules.mk share/lua/src/Makefile \
    share/common/marshal_x86_64.h share/io/luabase.cpp
do
    git -C "$build_rules" show "1c425175ae81a35b00d44e05e8e2c64513eabf05:$file" > "$client_build/$file"
done

for dir in common io lua mk rpc
do
    ln -s "../share/$dir" "$client_build/cnet/$dir"
done

make -C "$client_build/share/lua/src" -j4 liblua.a SYSCFLAGS=-DLUA_USE_LINUX
make -C "$client_build/cnet/gclient" -j4 -B gclient \
    'SHARE_SOBJ=../lua/src/liblua.a -ldl'

readelf -h -d "$client_build/cnet/gclient/gclient"
```

Контрольная сумма SHA-256 бинарника из прогона — `06d30111b6c5ff6c5e1fc5bde44ace9a6ec00bd63f27a78c30dd140a5a0274be`. Сборка использовала отладочную информацию. Из-за путей во временном каталоге хэш другой сборки может отличаться.

### Проверка собранного клиента

Команды из раздела выше повторно собрали клиент в новом временном каталоге. Затем новый ELF проверили в том же сценарии, что и готовый 1.7.2. Запустили обе карты и четыре учётки без специальных прав. За 70 секунд клиент авторизовал четыре сессии и добавил четыре роли. GS принял все четыре роли, но счётчик `ENTERWORLD` остался нулевым, изменений координат не зафиксировали. Переход на код клиента из 1.7.6 не устранил остановку после выбора роли. До подтверждения игровых действий этот прогон остаётся проверкой совместимости, а полноценный замер нагрузки с игроками открыт.

В дополнительном прогоне с одной обычной учёткой включили три счётчика в одноразовой копии клиента. За 70 секунд обработчик `GameDataSend` получил 365 пакетов, один из них дошёл до ветки `SELF_INFO_1`. Счётчик `TASK_DATA` остался нулевым. Это локализует остановку после получения первых игровых данных. Счётчик на входе в ветку `SELF_INFO_1` ещё не подтверждает, что клиент разобрал весь пакет. Причину отсутствия `TASK_DATA` предстоит установить. Диагностические изменения влияли только на журнал клиента.
