# Perfect World 1.7.6 Build 4311 — происхождение серверных файлов

Проверка от 16 ноября 2026 года. Официальная серверная поставка Build 4311 среди обследованных материалов **не подтверждена**. `Linear/PWServer176.7z` годится как опорный комплект для сравнения с ранее исследованной RuTracker VM. Все 12 сохранённых замеров этой VM совпали с текущим оглавлением Linear по размеру и CRC32. Комплект talolan связан с обоими по конкретным файлам VM и игровым бинарникам. Его диск VMDK отличается от диска RuTracker.

Сведения о текущих архивах взяты из их оглавлений и контрольных сумм. Данные об активных файлах, процессах и ссылках внутри гостя взяты из ранее собранного отчёта PW-Example. Цифры в таблицах означают размер в байтах и CRC32, если явно не указано другое.

## Как сопоставить с подтверждённым эталоном

1. Зафиксировать выпуск, регион и платформу серверной поставки. Для статуса «чистый эталон» нужен источник правообладателя с проверяемым манифестом или воспроизводимая сборка из подтверждённой полной исходной ревизии этого выпуска в описанной среде. Для исследованных `huzeming-176source` (`c0992a29`) и `code-bynary-176source` (`da5766ba`) предыдущий отчёт фиксирует отсутствующие `cnet/gamedbd`, `cnet/gdeliveryd` и `cnet/glinkd`, на которые ссылается `build.sh`. По этим деревьям привязка к бинарникам Build 4311 не установлена.
2. Посчитать SHA-256 контейнеров и снять оглавления `7z l -slt -ba -bd -- <архив>`. Для выбранного игрового дерева можно передать маски после пути архива, например `root/pwserver/gamed/gs*` или `root/pwserver/gamed/config/tasks*.data`. Из оглавлений сохранить путь, тип, размер, CRC32 и доступные атрибуты. Для полевых данных VM использовать `inventory.tsv`, `fingerprints.tsv` и `archive-match.tsv`.
3. Для вложенных 7z в этом ZIP можно повторить чтение метаданных без распаковки диска. При совпадении SHA-256 всего ZIP и подтверждённом методе `Store` начало записи `gs variants.7z` находится на смещении 104, серверного 7z — на 273 914 445. Смещения отсчитываются с нуля. Из каждого вложения взять первые 32 байта и последние 4 МиБ, сохранить их в разрежённый временный файл в исходных позициях вложения и прочитать `7z l -slt`. Для чтения дескриптора VirtualBox из первого блока серверного вложения достаточно сохранить первые 64 КиБ вместо 32 байт. Разрежённая копия предназначена для метаданных и указанного небольшого блока. При другом SHA-256 начала записей вычисляются заново из локальных заголовков ZIP.
4. Для VM сравнивать файловые деревья из снимков, полученных чтением, с относительными путями и отдельными полями для имени ссылки и разрешённой цели. Для выбранных файлов перепроверить SHA-256 исходных байтов. Разнести строки по внешней упаковке VM, окружению, серверной конфигурации, данным и бинарникам. Для несовпавших ELF записать архитектуру, Build ID и зависимости средствами статического анализа. У конфига сравнить набор ключей и пути к данным, у ресурсов — версию формата и отличающиеся записи.
5. Изменение считать установленным там, где показана пара «эталон → текущий файл» и конкретное отличие. Назначение подтверждать документацией, содержимым изменения или ссылкой из активной конфигурации. Авторство и исходное состояние оставлять открытыми там, где имеется только более раннее зеркало, метка `orig` или совпадение размера и CRC32.
